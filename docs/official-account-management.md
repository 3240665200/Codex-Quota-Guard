# 官方账户登录、授权与设备绑定

本模块将原有的“官方账户登记”扩展为后台管理授权、会话查看、管理员确认后的会话登出与串行登录绑定。原账户内部 UUID、团队关联、额度、邮箱配置不改变。它不是 Codex 推理请求转发器，不会自动触发官方登出。

## 重要现状

2026-10-15 经授权的真实浏览器读取中，账户列表与设备会话接口返回 200；独立 HTTP 请求曾返回 `cf-mitigated: challenge`。两种运行环境不可视为等价。另已修复真实数据中 `default` 与账户 ID 的相同别名条目，以及带小数秒的会话创建时间被误拒绝的问题。

因此，**本地模拟测试通过不代表真实服务器已经能访问会话接口**。这些是 ChatGPT 网站内部接口，没有稳定性承诺。代理也不保证解决 403。访问受阻时显示安全错误并停止，不能绕过验证或伪造绑定成功。

## 管理员操作流程

1. 通过 HTTP 或 HTTPS 登录本系统管理后台，推荐 HTTPS。允许 HTTP 的部署保留相同功能，页面会提示密码与导入的授权可能明文传输。
2. 如需代理，在“代理节点”添加节点或导入订阅内容／HTTPS 订阅链接。
3. 在“官方账户 → 账户管理 → 授权与会话”选择访问代理。已配置私有预置时可点击“使用预置授权”，无需手工填写 Cookie 或 Authorization；也可以通过“从本机参数文件填入”选择已有授权文件，再明确保存。
4. 如需正常登录官网，点击“在本机浏览器打开官方登录”，在自己的浏览器访问 [ChatGPT](https://chatgpt.com/) 并完成官方验证。本系统不能仅通过打开官网抓取跨站 Cookie，也不会自动完成 OAuth 登录；在官网登录成功不等于本系统已保存授权。
5. 授权文件为最多 **64 KiB** 的 UTF-8 JSON，必需 `requestedAccountId`、`authorization`，可选 `cookie`。账户 ID 为 1–160 个字母、数字、下划线或连字符；Authorization 必须是网页登录的 `Bearer …`，最多 16384 字符。Cookie 可省略、为 null 或空白，非空时最多 32768 字符，只允许 `__Secure-next-auth.session-token` 及其 1–3 位数字分块，不能重复，不接受挑战 Cookie。它不是邮箱密码、API Key、完整浏览器导出、curl 命令或 Codex `auth.json`。页面也兼容原有三段标签文本文件；服务器预置只接受 JSON。
6. 管理员主动提交后，后台使用候选授权验证账户身份与会话响应，核对既有连接版本和绑定身份后加密保存；失败保留原授权，不能把预置可用状态当成官方验证成功。成功更新授权仍按现有规则轮换连接修订号，原设备绑定需重新验证或绑定。
7. “官方账户 → 会话管理”是独立工作区：先选择账户，再查看会话、绑定记录和队列，执行预览确认后的登出或解绑。选择的代理故障时不会静默回退直连。

服务器 `0.3.20` 镜像不包含 Chromium，也不在管理页显示远程浏览器画面。开发、测试与发布使用相同预置／导入流程，无环境专属业务开关；既有手工授权导入可继续使用。私有预置通过后台运行时文件读取，状态和保存响应不回显原始秘密。不要把真实凭据粘贴到聊天、日志、仓库或公开包。

删除本系统保存的授权，只删除本系统连接记录，不调用官网退出。不同的真实官方账号不能无提示覆盖已验证的连接，必须先明确解除本地连接。

## 代理支持范围

- HTTP、HTTPS、SOCKS5 代理 URI，可包含代理认证。
- VLESS、VMess、Trojan、Shadowsocks 分享链接的受支持标准变体。
- URI 按行排列的订阅内容，以及 Base64 包装的同类内容；HTTPS 订阅 URL 为手动、一次性抓取导入，不持续订阅、不自动刷新已绑定节点。
- 本轮不接受完整 Clash YAML、sing-box JSON、任意分流规则、链式代理、插件、跳过证书验证或未支持的传输参数。遇到未知参数明确拒绝，不悄悄丢弃。

所有节点均通过独立 sing-box 1.13.14 子进程提供有期限的 loopback 入口。配置经 stdin 传递，不落盘明文、不放在命令行。官方接口用途只允许 `chatgpt.com:443`；应用层仍验证官方 TLS 证书。内核没有 TUN 权限，不修改系统代理，不对外开放代理端口；已选节点故障时不会回退直连。用户自己的浏览器网络由用户管理，不会因后台选择代理而自动改变。

订阅抓取只允许 HTTPS、公网地址、禁止重定向，并限制响应大小、数量及总耗时。代理服务器自身默认也限制公网；只有管理员通过服务器配置明确开启 `MANAGED_PROXY_ALLOW_PRIVATE_NODES=true` 后，才能使用私有网络代理端点，订阅 URL 不受此例外影响。

## 后台配置

每项加密密钥均为独立随机 32 字节 Base64，禁止与 JWT 或邮箱密钥共用：

```dotenv
OFFICIAL_SESSION_ENCRYPTION_KEY=
MANAGED_PROXY_ENCRYPTION_KEY=
MANAGED_PROXY_SING_BOX_PATH=/usr/local/bin/sing-box
MANAGED_PROXY_MAX_PROCESSES=4
MANAGED_PROXY_ALLOW_PRIVATE_NODES=false
```

新装 `deploy.sh init` 会生成独立密钥。已有安装的 `.env` 不会被覆盖：仅在从未配置对应密钥且数据库中没有对应密文时，才分别运行 `openssl rand -base64 32` 补充缺失项，将结果保存在受限 `.env`，不要公开输出。已有密钥不能重新生成，否则原密文无法解密；原值丢失时应恢复匹配的备份。数据库与密钥必须一同备份，密钥备份应另行加密保管。

缺少密钥时相应功能不可用；缺少官方会话密钥还会阻止建立官方连接及新绑定，不能用健康检查通过判断额度业务完整可用。授权、登录 Cookie、官方快照和代理配置均加密保存；页面/API 不回显秘密。普通用户无权访问管理接口。HTTP 支持不改变这些鉴权和存储规则。

私有预置由 `OFFICIAL_AUTHORIZATION_PRESET_FILE` 指向运行时 JSON 文件。Docker 默认路径是 `/run/secrets/official-authorization.json`，对应主机 `./secrets/official-authorization.json`；源码运行时可显式指定自己的私有文件路径。该设置只提供文件位置，不包含秘密，文件内容不能写进环境变量、前端构建或镜像。

没有预置或文件不可用时后端仍可启动，页面显示预置不可用，文件导入仍然可用。文件原始字节最多 64 KiB，提交时重新读取并验证；拒绝未知字段、重复字段、尾随 JSON、非法 UTF-8、控制字符和非字符串字段（可选 Cookie 可为 null）。页面读取后预置若发生变化，提交会拒绝旧修订号，需刷新后确认。文件可用不代表凭据未过期或官方接口可达。预置由管理员显式使用，不自动建立连接或绑定。

容器 UID 10001 必须能遍历挂载目录并读取文件。部署脚本只创建缺失的空目录，不修改原有文件 owner；可对精确目录与文件授予 ACL，详见[私有预置和权限说明](../deploy/docker/registry/README.md#私有授权预置)。预置与数据库密钥是不同材料，更新预置不应重置加密密钥。

## Docker、HTTP 与 HTTPS

源代码 Dockerfile 为 linux/amd64 固定下载上游 sing-box 1.13.14，校验官方发布的 SHA-256，并随镜像保留其 LICENSE。上游源码与许可：

- <https://github.com/SagerNet/sing-box/tree/v1.13.14>
- <https://github.com/SagerNet/sing-box/blob/v1.13.14/LICENSE>

当前服务器版本为 `0.3.20`，后端和网页均使用同版普通镜像，无浏览器后端。两个镜像及 `server-v0.3.20` 源码标签已发布，后端和网页的 `latest` 均指向本版本。旧版标签保持不变；本次不更新桌面，数据库仍为 V30，无新增迁移。镜像拉取部署见[registry 说明](../deploy/docker/registry/README.md)，下列 `--build` 命令用于源码部署。

传输策略由现有 `app.require-https` 统一控制。基础 Compose 设置 `APP_REQUIRE_HTTPS=false`，允许 HTTP 和 HTTPS 的私有预置授权、文件导入、会话操作和代理节点管理，不再限于 localhost；HTTP 前端仅提示风险，不禁用操作。**HTTP 会明文传输本系统密码与导入的官方授权，推荐 HTTPS。** 官方上游、代理订阅与邮箱各自原有的 TLS 校验要求不变。

HTTP 使用基础 Compose，在 `deploy/docker` 下执行：

```sh
mkdir -p secrets
docker compose --env-file .env -f compose.yaml config --quiet
docker compose --env-file .env -f compose.yaml up -d --build --wait
```

保留 `.env` 的 `PUBLIC_ORIGIN=http://服务器IP:8080`。HTTP 模式不需要 TLS 证书。若选择强制 HTTPS，可使用 TLS 入口配置：

1. 准备可信证书 `fullchain.pem` 与 `privkey.pem`。证书必须匹配访问域名或 IP，并让容器的非 root Nginx 用户能够只读访问；不要把私钥加入仓库。
2. `.env` 增加 `TLS_CERT_DIRECTORY=/绝对证书目录`，并把 `PUBLIC_ORIGIN` 改为证书对应的 `https://域名`。
3. 在 `deploy/docker` 下启动：

```sh
docker compose --env-file .env -f compose.yaml -f compose.https.yaml config --quiet
docker compose --env-file .env -f compose.yaml -f compose.https.yaml up -d --build --wait
```

HTTPS overlay 将 `APP_REQUIRE_HTTPS=true` 设为只接受 HTTPS，并把 HTTP 业务入口重定向到 HTTPS。只开放网站端口，后台和数据库不直接暴露公网。TLS 入口覆盖转发头，后端只接受受控反代流量，不能信任客户端自行填写的 `X-Forwarded-Proto`。使用其他反代时按同样原则配置，不通过伪造请求头绕过 HTTPS 策略。

HTTP 与 HTTPS 均使用同一 `runtime` 目标、sing-box 和只读预置挂载，保持非 root、`cap_drop: ALL`、`no-new-privileges` 及只读根文件系统，无浏览器 seccomp 或额外权限。升级旧浏览器部署时，从命令中移除 `-f compose.web-login.yaml`，不再使用 `-browser` 镜像；保留原数据库、密钥与所选 HTTPS 配置，见[部署升级说明](../deploy/docker/registry/README.md#从-0318-或-0319-升级)。

## 本机测试服务的生命周期

管理网页使用 `http://localhost:8000`，桌面客户端的服务器地址使用 `http://127.0.0.1:18080`，两者不是同一端口。网页后台不依赖 Quota Guard 桌面客户端。

Windows 本机预览由 `scripts/windows/start-admin-preview.ps1` 启动。启动器使用独立、隐藏的管理进程承载网页与 Java 后端，不将服务留在调用终端或编程工具的临时进程组中；无法确认独立启动时明确失败，不静默回退。保留原有 DPAPI 配置和加密密钥，不注册开机任务或 Windows 服务。

每次启动在预览目录的 `runs/<runId>/` 内保存状态和生命周期事件，记录实际监听进程的身份、启动结果与退出码，不记录密码、Cookie 或授权值。停止时使用该次运行对应的停止入口，只关闭该次运行持有的子进程；不要按 `java.exe`、`node.exe` 名称批量结束进程。不会在服务异常退出后自动重发官方登出请求。

如果登出后显示 `Failed to fetch` 或“中央后台不可用”，先检查两个端口及该次运行状态。官方授权失效、用量门禁与本地服务停止是不同问题，不能仅凭发生先后就认定原因。此次问题已确认最新登出请求全部被官方接受，但旧进程没有留下退出记录，无法还原是谁终止了它们；隔离模拟测试和独立启动用于验证与修复已发现的生命周期隐患，不代表重复执行过真实登出。

## 管理员手动登出

授权页面提供三个独立操作，均先读取新鲜官方数据、显示预览，再要求明确确认；打开页面、刷新、登录辅助和统计程序不会触发它们。

- **登出所有会话**：调用官网的全局登出操作，可能影响该官方账号的已绑定、受信任和当前管理会话，后台授权也可能失效。预览只列当前可见记录，不保证是全局操作的精确最终范围。此功能不调用“撤销受信任设备”接口。
- **登出所有未绑定会话**：只处理预览中明确未绑定、非受信任、非当前管理会话且 ID 唯一的目标。状态未知、重复/缺失 ID、已有 ACTIVE 绑定及受信任设备均排除。逐个发送前再次读取目标状态，变为受信任等情况会停止，不扩展到新出现的会话。
- **登出选中会话**：在官方设备会话表中勾选目标，再生成预览并确认。只处理本次明确选择的会话，不自动包含其他设备；已绑定或受信任的选中会话也可能被登出，确认前需核对提示。此操作不撤销受信任设备资格。当前管理会话、当前身份或受信任状态未知、缺失或重复 ID 的行不能单独登出；需要全局退出时使用“登出所有会话”。改变选择或刷新快照后需重新预览。

“当前会话”以官方对此次授权返回的标记为准，不等于整台电脑上的所有会话都被保护。系统按准确的 session ID 判断绑定；同一电脑上另一个明确未绑定、非受信任且非当前的会话，仍可能成为清理目标。不得仅凭设备名称相同就推断是同一个会话。

确认计划按管理员、账户、授权版本、绑定与会话状态校验，并有短有效期。执行时与更换授权、建立绑定、登录助手和删除账户互斥。官方 POST 不做应用层自动重试；每次发送前先保存操作记录，关闭管理页面也可以重新查看进度。

“官方已接受”不等于所有设备已即时离线，官方生效可能延迟。超时/响应不明确显示 UNKNOWN 并保留本地保护锁；管理员必须到官网核对结果、明确确认后才可解除保护。解除保护不撤销、不重发先前的官方请求。实现验证使用模拟接口，未对真实账号执行登出。

选中登出的 ACCEPTED 或 UNKNOWN 目标会使对应本系统绑定失效；明确失败、未尝试及未选中的绑定保留。执行期间由账户操作锁阻止使用旧绑定，收尾或核对解除保护时根据持久操作记录处理。UNKNOWN 包含“已记录派发意图，但进程中断导致无法证明是否送达”的情况，会保守要求该目标重新绑定；系统不会猜测成功或自动重发。此扩展使用 V27 仅增加 SELECTED 计划类型，不删除既有计划和绑定。

## 首次登录排队绑定

桌面登录本系统后显示“本设备官方会话绑定”引导。队列由后台数据库协调，同一官方账户只有一个用户进入完整的“新鲜 before → 用户在官方 Codex 应用正常登录 → 新鲜 after → 用户确认归属”周期。邮箱验证码到达不会结束该周期。只有唯一新增的 Codex 会话可供确认，零个或多个候选都不自动绑定；已登录的旧会话也不会被猜测为本设备。

授权失效、团队变化、设备撤销、快照不完整或并发更改都使尝试失败。0.3.16 起，排队最长 60 分钟，取得新鲜登录前快照并发放名额后有完整 30 分钟登录时间。队列由中央后台持续推进，不再依赖页面每两秒请求 prepare。

获得名额后取消、超时或失败，会撤销本次操作令牌并进入约 30 秒自动整理期；随后后台重新获取新鲜快照，再给下一位用户发放名额，不需要管理员手动解锁。官网暂不可读时按 5、10、20、40、60 秒上限自动退避，排队仍受总期限约束，不能以失败的快照授予登录许可。未发放名额的取消不必等待该整理期。旧版遗留的暂停队列也由新后台按相同流程自动整理。

任务代次和操作令牌只防止**旧后台请求的结果**写入新任务，不会让第三方官网会话携带本系统标识。交接快照前已出现的旧会话会被排除，零个或多个新增候选不会自动绑定；但上一位取消后仍在不受控的官网继续登录，且恰好在下一人的快照之后产生唯一新会话时，仍无法仅靠列表证明物理归属。请停止已取消的官方登录流程，用户确认仍不可省略。

已确认记录关联本系统用户、安装设备 UUID、设备登记、官方账户和官方 session_id，并保存 `SERIAL_LOGIN_DIFF` / `USER_CONFIRMED_INFERENCE` 来源。**它是串行差分加用户确认，不是官方提供的硬件身份认证；无法阻止系统之外的人员同期登录。** 绑定动作本身不自动执行官方下线。

复用现有 `meter-device-id.txt` 中的持久 UUID，正常升级保留，不是不可克隆的硬件指纹。当前版本的安装 UUID 与 meter 登记 UUID 必须一致，后端验证其属于当前系统用户。现有设备已属于其他系统用户时仍拒绝直接接管；不通过重写 UUID 绕过既有设备所有权保护。结束或失效的绑定保留历史。

## 登录辅助的实时状态与刷新恢复（0.3.16）

绑定和邮件任务状态使用 SSE 单向通知，经本机 Java 与 Rust 桥接到页面；不放宽页面网络策略，也不把后台登录令牌交给页面。中央共享检测数据库状态的变化，变化时才发出无敏感内容的通知；15 秒心跳仅用于连接保活，不刷新页面。断线有界退避重连，重新连接后读取当前状态，不自动重发绑定、确认或邮件监听请求。原有设备权限检查继续独立执行。

邮件监听由后台持有，默认最长 10 分钟；刷新、切换菜单或关闭页面仅断开实时订阅，不取消监听。当前用户再次打开页面时通过鉴权的 current 接口恢复同一个任务，不重开连接、不重设新邮件游标。验证码结果仍只保留 60 秒，不写入本地存储或 SSE 通知；显式取消或退出系统登录会结束对应监听。此恢复能力针对页面生命周期，不应将进程崩溃后的残留状态当作连接仍在运行的证明。

中央升级会通过 V29 只增加自动交接的代次与调度字段，不删除用户、用量或绑定历史。切换前停止旧中央实例，不能混跑不检查任务代次的旧写入实例。迁移只向前执行；出现问题应停新进程并修复，不直接删列或用旧实例继续写。新版桌面显式请求队列元数据版本 2；旧桌面仍收到原有响应字段，但实时通知与恢复界面需要新版桌面才能使用。

## 管理员解绑会话

在“官方账户 → 授权与会话 → 设备会话绑定记录”中，对“已绑定”记录点击“解绑会话”，核对系统用户、设备 UUID 和官方 Session ID 后确认。

解绑仅结束本系统保存的那一条关联，保留绑定与结束时间历史，不调用官方登出、不删除设备登记、不停止统计或清除用量。受影响客户端再次校验时将仅开放“登录辅助”，用户可以重新发起绑定。重新绑定仍需经过串行登录识别流程，不会自动认领原来的官方会话。

后台只允许管理员操作并核对记录所属官方账户；同一记录重复提交不会覆盖原结束时间，也不会影响后来的新绑定。官方登出执行中或结果待核对时暂停解绑，避免改变正在操作的目标。解绑完成后旧登出预览失效，需要重新预览；刷新绑定列表失败时页面不会继续显示旧的有效归属。

此功能只需更新中央后台和管理网页，已安装 0.3.14 桌面客户端无需为此重新打包。增加功能不代表已替管理员操作真实绑定，仍由管理员确认执行。

## 桌面会话绑定门禁（0.3.14）

登录或恢复系统登录态后，客户端先向后台验证“当前系统用户 + 本安装设备”的有效绑定。检查中、网络失败、没有绑定或绑定失效时，仅开放“登录辅助”，其他业务菜单和内容均禁用；切回窗口和定期检查会重新验证。页面收到绑定拒绝后立即回到登录辅助，不清除仍有效的系统登录态。

本机 Java 和中央 API 都执行校验，不能只修改前端菜单或伪造 `allowed: true` 解锁。中央校验 ACTIVE 绑定、设备登记归属与有效期、用户状态、当前团队与官方账户、授权版本，以及登出保护锁。正常完成“未绑定会话清理”不会误使保留的有效绑定失效；全部登出、授权替换、团队变化或设备撤销仍要求重新确认绑定。

登录、设备配对、验证码、绑定流程和管理员官方登录助手为必要的启动入口。管理员网页按 ADMIN 权限独立管理，不要求该浏览器绑定；独立统计服务使用自己的设备授权，不受桌面菜单门禁阻断。安装 UUID 是持久安装标识，不能宣称能抵抗本机管理员克隆或篡改。

## 0.3.14 手动验收

1. 保留原加密密钥；本节记录 0.3.14 的 V24–V27 功能验收，当前 0.3.20 后台已包含 V30。当前基础部署允许远程 HTTP 与 HTTPS，推荐 HTTPS；启用 HTTPS overlay 的部署仍强制 HTTPS。客户端至少使用 0.3.14，旧客户端没有设备门禁请求头；新增管理员解绑和选中登出不需要重新打包该客户端。
2. 当前版本由管理员使用预置授权或导入授权文件，检查后台验证后的账户身份和会话；不需要服务器浏览器或桌面助手代为获取网页 Cookie。
3. 给测试用户配置团队、官方账户与有效设备登记。用测试用户登录桌面，确认只有“登录辅助”可用；申请绑定并等待“可登录”。
4. 在官方 Codex 完成本次登录，回客户端点识别，核对唯一候选后确认。后台应显示对应用户、设备 UUID 和 Session ID；门禁重新验证通过后开放其他菜单。
5. 另用两个测试设备检查排队；测试超时/取消/多个候选时，应拒绝误绑定并要求管理员核对。管理员登出操作会真实影响官方会话，请先核对预览与警告，不要在正在工作的会话上随意测试。
6. 在管理员撤销绑定、设备或更换团队后，客户端再次验证应锁定业务菜单。断网时也保持锁定，不把旧缓存当作新授权。
7. 覆盖安装后确认统计程序运行版本为 0.2.3。完成配对，从系统托盘完全退出桌面，在官方 Codex 产生新用量；通过后台查看设备心跳与逐笔用量。此项真实验收需用户操作，本轮自动化使用模拟日志与后台，未关闭用户实际客户端或运行真实冲突守卫。
