# 团队与个人 Token 策略

本页是**当前实现**。历史方案中的“托管 Codex 账户、按官方百分比分配个人额度”已停用；官方登录留在用户电脑，后台不保存或分发官方凭证。

## 策略来源

管理员在“团队与额度策略”中设置团队默认的滚动 5 小时和 7 天 Token 上限，再把系统用户加入团队。用户管理页还可为单个用户设置覆盖值。每个窗口独立按以下顺序解析：

```text
用户个人 Token 上限（非 null） → 所属团队默认 Token 上限（非 null） → 未配置
```

- `null` 表示继承下一层；两层都为 `null` 时显示“未配置”，不是无限额度。
- `0` 是有效上限，表示该窗口无剩余额度，不可当作“未配置”。
- 5 小时和 7 天分别计算，单位均为 Token；不把官方额度百分比换算为 Token。
- 团队停用会使本系统额度状态显示不可用，但本机 Rust 服务仍继续上报可读取的用量，避免统计空洞。

## 用量计算与展示

Rust Windows 服务（或桌面打开时的 Java 回退扫描器）从本机 Codex 会话日志提取新增用量，中央 Java 服务按系统用户和事件 ID 幂等入库。5 小时/7 天窗口按**中央服务接收时间**滚动汇总；`remaining = max(0, limit - used)`。后台和桌面端分别显示“已上报用量”“个人上限”“剩余量”和最近一次上报时间。

官方 Codex `account/rateLimits/read` 返回的是**官方账户整体**窗口与百分比，不是某个 Quota Guard 用户的消费。它单独作为参考显示，不能复制给团队成员、不能与本系统 Token 上限混算；缺少的官方窗口标为未提供。

## 限制与操作语义

- `allowed` 和用尽原因是本系统的**提醒状态**，不是官方 Codex 的执行授权。官方请求不经过中央 Java，因此本项目不能在个人额度用尽时阻断官方 CLI/桌面应用。
- 管理员的“强制下线”仅撤销 Quota Guard 系统会话，不会退出官方 Codex 会话。已配对的 Rust 服务仍会继续上报原绑定用户的用量，直至设备令牌被管理员撤销或到期。
- 设备心跳离线、尚未配对或没有可读的会话日志时，`0 Token` 只能表示**尚无已接收事件**，不能证明真实用量为零。
- 管理员/root 可停用本机服务或修改本机文件；当前统计不是不可绕过的计费网关。若将来需要硬性额度拦截，必须让官方请求经过受控执行/代理链路，并重新评估合规与安全边界。

具体数据流和安全边界见[当前系统架构](current-system-architecture.md)。
